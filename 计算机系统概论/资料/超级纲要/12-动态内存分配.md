# 动态分配：malloc 给了你一块内存，还给了你哪些责任

数组大小要等读入文件后才知道，函数结束后对象仍要存在，这时可以使用动态分配。malloc按请求字节数提供一块可用存储；free结束这次分配对象的使用。难点往往不在函数名，而在“谁拥有这块对象、长度是多少、哪些地方仍握着地址、何时最后一次使用”。

本章先从使用者角度写安全代码，再拆开分配器内部的块、空闲表、分割和合并。理解内部实现可以解释性能与碎片，但不能把某个教学分配器的布局当作所有malloc的固定规格。

## 请求字节数，返回的不是初始化数组

`malloc(n)`请求n字节，不是n个int。若要n个int，常写`int *p=malloc(n*sizeof *p);`。`sizeof *p`由指针所指类型决定，避免类型改了而常量大小没改。使用前应检查乘法溢出与分配失败。

malloc成功得到的内容未初始化，不能读来当已有合法值。你需要给每个将要读取的元素赋值，或者按需求使用其他初始化方式。返回地址满足接口规定的对齐保证，但超大对齐需求需要专用接口，不能认为任何自定义对齐都自动满足。

free要求传入空指针，或仍有效、且来自兼容分配接口的原始分配起点。传入p+1、栈数组地址或已经释放的指针都不合法。`free(NULL)`是允许的无操作。释放以后旧地址可能仍在变量里，但对象已失效；字节暂时没变，不会延长生命周期。

## 算例一：分配并初始化n个元素

设n来自可靠解析后的size_t。先检查`n>SIZE_MAX/sizeof *p`则拒绝；再请求n×sizeof*p字节；对非零请求检查返回是否为空；最后在`0<=i<n`范围逐个初始化。用完调用free，并在本作用域把p设为NULL可以减少误用，但不能自动清除别处保存的别名。

例如n=3、sizeof*p=4，需要12字节。p指向起点B，p[0]、p[1]、p[2]起点分别B、B+4、B+8。最后一个元素占B+8至B+11。p+3可作为尾后指针，不能读写；`free(p+1)`也不成立，因为它不是分配起点。

n=0要单独说明接口策略。malloc(0)在C17下有实现规定行为，可能返回空指针或一个不可用于访问的独特指针，后者仍可free。应用可以明确把零长度当空数组，避免写出依赖某一种返回形式的代码。

## 从头文件到free，完整运行一次

先在同一个函数里完成整段生命期，不引入输出参数。n=3，每个int按本书平台占4字节，先请求12字节；分配成功以后才有可写的p[0]到p[2]，依次填0、1、2，读取输出，再释放。这份程序把n=0规定为空数组，不请求存储。

```c
#include <stdint.h>
#include <stdio.h>
#include <stdlib.h>

int main(void) {
    size_t n = 3;
    int *p = NULL;
    if (n > SIZE_MAX / sizeof *p) {
        fputs("request too large\n", stderr);
        return EXIT_FAILURE;
    }
    if (n != 0) {
        p = malloc(n * sizeof *p);
        if (p == NULL) {
            fputs("allocation failed\n", stderr);
            return EXIT_FAILURE;
        }
    }
    for (size_t i = 0; i < n; ++i)
        p[i] = (int)(i % 10);
    int status = EXIT_SUCCESS;
    for (size_t i = 0; i < n; ++i) {
        if (printf("%d\n", p[i]) < 0) {
            status = EXIT_FAILURE;
            break;
        }
    }
    free(p);
    if (fflush(stdout) == EOF) status = EXIT_FAILURE;
    return status;
}
```

将代码存为alloc-demo.c，可用`cc -std=c17 -Wall -Wextra alloc-demo.c -o alloc-demo`编译。n为3时输出三行0、1、2。假设成功地址为B，初始化后的三个对象从B、B+4、B+8开始；free(p)结束的是这次分配，p变量不会因此自动变为NULL。

把n改成0，两个循环均零次，p一直为NULL，free(NULL)合法。把n改成SIZE_MAX，本环境的sizeof *p为4，会在乘法前拒绝；不能先算n*4再检查已经绕回的结果。sizeof *p这里只询问类型大小，不实际沿NULL访问int。

## 所有权：谁最后负责free

所有权不是普通C类型系统自动替你保存的信息，而是程序设计约定。函数返回动态分配对象时，应说明调用者负责释放；函数只借用外部缓冲时，不应偷偷释放它。两个模块都认为“对方会释放”会泄漏，两个模块都认为“我应该释放”会重复释放。

可以在每个指针旁写“拥有”或“借用”。拥有指针负责最后释放，借用指针只在规定时间内使用，不延长对象生命。若数据结构中有多个别名，需要更具体的所有权策略，例如唯一拥有者、引用计数或外部生命周期管理。把每次malloc与某次free按文本数量配对不够，还要确认所有执行路径和所有别名关系。

把p设NULL只影响p这个变量。若q早已等于p，free(p)后q仍是悬空指针。许多释放后使用错误正来自“我已经清空p了，所以安全”的误判。

## 让函数把新地址交回调用者

现在增加一个需求：分配工作交给make_array，调用者main还要在函数返回后使用对象。若只把main中p的当前值传进去，函数修改自己的指针副本，main的p不会自动改变。需要把“main的p这个变量的地址”传给函数，让函数能写回它。

设main的p变量位于0x5000，初值NULL。调用make_array(3,&p)时，参数out保存0x5000。函数内另有局部指针p，假设malloc成功后它保存0x6000：

|表达式|在这份状态里访问什么|含义|
|---|---|---|
|out|函数参数里保存的0x5000|main的指针变量的位置|
|*out|0x5000处的指针对象|main将要使用的地址|
|函数局部p|函数自己的指针对象|malloc给出的0x6000|
|`**out`，成功写回之后|0x6000处的第一个int|数组第0项|

`*out=p`把0x6000写进main的指针变量，没有复制整个数组。函数返回后，函数局部p结束生命期，但分配对象仍在，main保存的新地址仍可使用。`int **`中的两层星号分别对应指针对象和最终int；`sizeof **out`为单个int大小。

下面是可与前面头文件配合的函数定义，另需包含`<stdbool.h>`。out必须指向一个仍存活、可写的int*变量，且该槽位没有尚未释放的旧拥有对象；本例调用者的p尚未获得分配。函数不会替你释放被覆盖的旧地址。返回false代表请求过大或分配失败，返回true后由调用者最终free：

```c
static bool make_array(size_t n, int **out) {
    *out = NULL;
    if (n == 0) return true;
    if (n > SIZE_MAX / sizeof **out) return false;
    int *p = malloc(n * sizeof *p);
    if (p == NULL) return false;
    for (size_t i = 0; i < n; ++i)
        p[i] = (int)(i % 10);
    *out = p;
    return true;
}
```

调用者可写`int *p; if (!make_array(3,&p)) { /* 报错并退出 */ }`，成功后按前一程序使用并free(p)。函数开始把*out置NULL，因此失败不会留下一个假装成功的旧地址；零长度成功得到NULL。给每个对象分开标生命期，比看哪个变量也叫p更可靠。

## 算例二：realloc为什么不能直接覆盖原指针

错误模式是`p=realloc(p,new_size);`。如果失败返回NULL，原分配仍有效，但原地址被覆盖，程序失去了释放和继续使用它的入口。应先用临时指针接结果，成功后再更新p。

例如原p指B、容量100字节，请求200失败。临时变量tmp=NULL，而p仍指B，可选择保留旧对象、报告错误或释放。成功时，返回地址可能仍是B，也可能是新位置C；旧对象的前min(旧大小,新大小)字节内容被保留，扩展部分未初始化。成功后旧指针及旧对象内部的地址都不能再当作原对象访问依据，即使数值碰巧相同也要遵循新对象关系。

如果你保存了`int *q=&p[2]`，realloc移动后q不会自动跟着更新。可保存元素下标2，成功后重新计算`q=p+2`。请求大小为0又有额外实现与版本规则，本书建议应用显式用free处理清空，避免把零大小realloc的历史差异藏进普通扩容路径。

## 分配器看到的是一串块

先看一个具体布局模型：块按8字节对齐，头部8字节；malloc请求13字节载荷。若这个块从0x1000开始，先有8字节头部，再有13字节用户空间，共21字节，向上补到24：

|地址范围，含两端|用途|字节数|
|---|---|---:|
|0x1000—0x1007|头部，记录本块大小和状态|8|
|0x1008—0x1014|本次请求的载荷|13|
|0x1015—0x1017|为块对齐留下的填充|3|
|0x1018|下一个块可能开始的位置|不属于本块|

用户得到的p为0x1008，不是块起点0x1000。它可以按请求使用13字节，不能把填充当作额外申请到的空间。块总占24字节，13字节请求之外的11字节由头部8和填充3组成。

教学分配器常把堆区域分成若干块。每块有头部记录块大小与分配状态，部分设计还有脚部。已分配块中包含用户载荷与可能的对齐填充；空闲块可存链接字段。用户拿到的p通常指载荷起点，不是整个块头。

内部碎片是已分配块内部无法交给用户有效使用的部分，例如对齐、最小块限制和管理开销。外部碎片是空闲总量不少，却分散成许多小块，无法满足一块大的连续请求。两者成因不同，不能只看“还有多少空闲字节”就判断能否成功分配。

这是用于手算的分配器，实际malloc的头部、对齐、最小块和开销可能完全不同。

## 算例三：首次适配、分割与剩余块

空闲表按地址有块A=32、B=80、C=48字节。请求最终块大小40字节。首次适配从头找，A不够，B够用，选择B。若最小合法空闲块为24字节，可把B分成40字节已分配块与40字节空闲块。

若请求最终大小64，B剩16字节，小于最小合法空闲块，不能留下一个连头部与链接都装不下的小碎片；常见策略把整个80字节给这次请求，内部多出16。最佳适配会寻找足够大的最小空闲块，此题40请求时可能选48，是否可分割仍受最小块规则限制。

首次适配不保证碎片最少，最佳适配也不保证整体速度或未来碎片最优。请求序列未知，局部最合适不等于全局最合适。分离空闲表、按大小分类等设计试图改善查找与利用率，但每项都有管理成本。

## 再做一道完整空闲块序列题

采用块大小已包含管理开销的教学模型，起始有一个128字节空闲块，最小可分出的空闲块24字节，首次适配，立即合并。依次请求A32、B40、C24，然后释放B、释放A，再请求D64。请每一步画地址区间。

A占0至31，剩32至127共96；B占32至71，剩72至127共56；C占72至95，剩96至127共32。释放B后，32至71空闲40，两邻A与C都在用，不能合并。释放A后，A与B相邻同为空闲，合并成0至71共72；C仍占72至95，后面96至127空闲32。

D需要64，首次找到前面的72。若分割，剩8小于最小空闲块24，因此整个72交给D，形成8字节额外内部余量。剩余独立空闲块仍为32。若有人把前72与后32加起来当104连续可用，就漏掉中间仍活着的C24。

现在释放C，会与后32合成56，但不能与D合并，因为D仍在用。再释放D，三个相邻范围合并回128。每次检查“实际地址是否相邻”和“是否当前空闲”，比只在链表里找前后节点更清楚。

这道题的块大小已经包含头部等管理开销，不能再额外加一次头部。题目前提写清，才能防止两套模型叠加。换成请求载荷大小的题，第一步应先算实际块大小再做同样流程。

横轴是同一块堆的相对字节偏移，所有区间右端不包含。例如B占`[32,72)`，正好40字节；这与正文用“32至71”描述同一范围。每一行总长度仍128，颜色改变表示所有权/状态改变，不表示把不相邻地址凭空搬到一起。D请求64却占72那一行，8字节余量在D块内部，没有另画成一个非法小空闲块。

显式空闲表还需同时变化：释放B后空闲节点为`[32,72)`、`[96,128)`；释放A后前者必须被`[0,72)`替代，不能两个都留下。D占前72后，空闲表只剩`[96,128)`；释放C后变成`[72,128)`；释放D后才只剩`[0,128)`。物理块图与链表节点图要描述同一批空闲范围。

## 释放后为什么要合并邻居

相邻空闲块可合并成更大的空闲块，减少外部碎片。合并要区分前邻、后邻分别已分配或空闲的四种情况。若有边界标记，可在常数时间定位相邻块大小与状态，但仍要正确维护空闲链表。按地址相邻与在空闲链表中相邻不是同一回事。

例如内存从低到高为已分配A32、空闲B48、已分配C32、空闲D64。释放C后，它可与左右空闲B、D合并为144字节块。若只把C加入空闲表不合并，空闲总量仍是144，却最大单块只有64，对100字节请求可能失败。

不能合并两个不相邻块，即使它们在空闲链表上碰巧前后相连。合并改变的是连续地址范围，链表顺序只是一种查找组织。

## 算例四：四种合并情况逐项检查

假设释放当前块X。前后均已分配时，只把X标空闲并登记；前空闲、后已分配时，前块与X拼接，更新总大小；前已分配、后空闲时，X与后块拼接；前后均空闲时，合成前+X+后一个块。

若使用显式空闲链表，合并之前要把参与的旧空闲节点从链表摘除，再插入合并后的新节点，或采用等价且保持一致性的更新顺序。否则链表可能同时保留指向块内部的旧节点，下一次分配会把同一内存交给两个请求。

验证可以画两张图：一张按实际地址排块，一张画空闲表指针。释放与合并后，确认每个空闲地址范围只出现一次，块不重叠，头脚一致，前后指针互相对应。只核对总字节数，会漏掉严重的链表损坏。

## 泄漏、越界、重复释放、释放后使用怎样区分

泄漏是对象仍被分配器视为使用中，但程序已无法按设计释放或不再需要却长期不释放。越界是访问对象范围外的字节。重复释放是同一分配对象生命周期结束后，再次把旧地址交给free。释放后使用是对象已结束，还通过旧指针读写。

一个错误可引发其他症状。例如越界写坏下一块头部，当前写入时未立即崩溃，下一次free才被分配器检查发现。崩溃栈显示在free，并不说明free调用本身最先错；要沿对象与块边界回查谁先改坏管理信息。

垃圾回收与引用计数是另外的自动管理思路，各有成本和边界。课程中的C显式分配要求你自己表达所有权。不能通过“进程结束系统会回收”替代长期运行程序的内存管理，服务可能在结束前就耗尽资源。

## 峰值利用率与吞吐量，分配器常要取舍

课程实验可能同时衡量有效载荷占堆大小的比例，以及单位时间能处理多少请求。把每次请求都细拆到最小，可能省空间却增加查找与管理；保留大小类别和快速缓存，可能提高速度却暂时留住更多空闲内存。设计不是只优化一个数字。

计算利用率时，应明确分子是某一时刻用户有效载荷峰值，还是整段请求累计量。后者把已经释放的历史请求重复算入，可能得到超过100%的荒谬结果。分母也要按实验定义，是实际扩展的堆字节数，还是某个时刻驻留内存，二者不能混用。

玩具序列：先分配100字节A，再分配100字节B，释放A，再分配80字节C。累计请求280不代表同时需要280；峰值用户载荷是200。若分配器始终占用256字节堆，按这一简化口径峰值利用率为200/256，而非280/256。时间线能把“累计”与“同时活着”分开。

## 空闲表损坏为什么会延迟爆发

显式空闲表常把前后链接存进空闲块载荷。用户对象释放后，这些旧载荷字节可能立即变成分配器管理字段。若程序继续通过旧指针写“我自己的数组”，其实是在改空闲链表。下一次malloc遍历时才崩溃，错误位置远离最初释放后使用。

这解释了为什么free后打印旧对象做调试也不可靠。对象已不属于你，分配器可以把内容改作任何合法内部用途。把free后的地址当作仍可读快照，会与实现争用同一存储语义。

调试器中的内存断点有时能找出谁改坏某字节，消毒器也能标出释放后访问。若错误只在高负载下出现，还要排查跨线程所有权：一个线程释放对象时，另一个是否仍借用。分配器内部线程安全不等于应用对象生命周期自动安全。

## 扩容策略为何影响总复制量

动态数组每次只增加一个元素的容量，插入第k项时可能复制前k−1项，总复制量约1+2+…+(n−1)，为二次增长。若容量每次翻倍，复制规模约1、2、4、…，总量小于2n，因此平均每次插入的复制开销可以为常数数量级。

这是摊还分析，不保证每次插入都快；碰到扩容的那次仍可能复制很多项。翻倍也会留下空余容量，空间与时间有取舍。实际增长因子、峰值内存和realloc是否能原地扩展都会影响表现。要从请求序列和对象需求选择策略，不能只凭“malloc很快”忽视频繁移动。

练习：容量从4翻到8时已有4项，新插入第5项，realloc成功移动到新地址。旧元素指针是否自动有效？答案是否；应重新从新基址与下标计算。摊还时间结论不会消除旧地址失效的问题。

## 自己做，再看答案

练习一：总空闲160字节，由不相邻的40、40、80三块构成。能否满足最终块大小100的连续请求？

答案：按这个分配模型不能，因为最大连续空闲块只有80。总量够而单块不够是外部碎片。不能把不相邻的40与80简单拼成一段地址，除非使用不同的虚拟映射或应用级分段结构，而那已不是本题分配操作。

练习二：p与q指向同一分配对象，free(p)后将p=NULL，q还能用吗？

答案：不能，q仍指向已结束的对象。p置空只改一个指针变量，不会遍历程序清除所有别名。应由所有权设计保证借用者在释放前停止使用。

练习三：请求17字节，头部8字节，对齐8字节，最小块24字节，实际块至少多大？

答案：载荷加头部25，向上对齐到32；32也大于最小块24，所以取32。总开销15字节，其中8头部、7对齐填充。不能先把17对齐到24后忘记头部，虽然此题碰巧再加8也得32，步骤必须与给定布局一致。
